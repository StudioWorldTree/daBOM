## Comparison and return findings

The current contract answers the architectural concerns above and resolves the three prior send-back findings. I compared against the living ingest spec and current code, then checked the proposed `add-evidence` interface solely as an unlanded dependency. I did not review `add-link-extract`.

1. **Locator boundary resolved.** Delta line 5 and design lines 15–19 distinguish absent/blank input from unsupported locators, require trim-based identity, pin kind defaults and existing-kind retention, and reject invalid incoming locators with atomic 422. Design explicitly acknowledges the narrower input contract. Retained legacy `items.source` values are not revalidated. This agrees with the dependency's new-source contract while preserving its legacy-data exception.
2. **Persisted facts resolved.** Delta lines 7 and 11 and design lines 25–31 record trimmed manufacturer/MPN values, omit facts for whitespace-only values that persist nothing, and preserve notes exactly. Notes eligibility is non-null, so an explicitly empty notes string remains eligible on create. Matched notes and populated fields are protected. This matches `createIngestRow` and `matchIngestRow`; the dependency does not require enrichment values to be non-empty.
3. **Attribution resolved.** Delta lines 9–11 apply the same supporting-document rule to creates and null fills. A child inherits the request source rather than a parent's override, matching `walkIngest`. An older item source stays untouched while a new fact cites the current document. The proposal's What and delta line 5 require links for request, node, and supplemental locators; the citation selects the singular supporting document. Supplemental links do not claim that every document supports every field.

The transaction, repeat-POST, no-thought, and no-quote requirements remain explicit. Evidence writes can use the existing ingest transaction without changing resolution order, floor/cycle guards, or the living response contract. No second persistence path is required.

## Steelman against the independent take

My initial preference for preserving legacy source behavior could argue against rejecting previously accepted `file:` strings or treating a blank node source as absent for citation. The author has made both choices explicit. Evidence needs a usable locator; old stored strings remain protected, and citation selection need not rewrite the legacy item column. In particular, current `node.source ?? source` item persistence must not silently become blank-aware merely because the evidence citation is blank-aware. That distinction follows from the unchanged item semantics and the explicit citation rule, rather than requiring a competing design.

The revision adds padded create/match, invalid-locator, and inheritance scenarios. It does not separately enumerate the previously requested whitespace-equivalent-locator and blank-match scenarios. Their outcomes are now fixed by normative text, so this is implementation coverage to carry into the existing API-test task, not an unresolved architecture decision. Include null-source deduplication and failure after evidence writes when exercising the stated retry and rollback requirements.

The matched-MPN test needs a genuinely matchable fixture: an existing SKU with both identity fields null and no competing MPN match satisfies the current guards (`bom.ts:682–698`). An item with a populated manufacturer and a differing incoming identity would correctly remain a 409. The scenario's phrase “matched by sku” does not authorize relaxing that guard. Likewise, the parent in the inheritance scenario needs an eligible persisted field for its asserted enrichment.
