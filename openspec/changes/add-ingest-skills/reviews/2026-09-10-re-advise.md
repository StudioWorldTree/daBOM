## Independent take (written before design / tasks / prior review)

Sources: packet Why, `openspec/specs/bom-ingest/spec.md`, the
`ingest-skills` living stub, `api/app.ts:578-621` (415 gate and the
`POST /ingest` route), `api/schemas.ts:336-366` (`IngestNode`,
`IngestRequest`). No `skills/` directory exists yet.

1. Pin: the skill's product is an `IngestRequest` file on disk, and the
   POST reads that file. Ingest is write-through with no draft store, so
   the file is the only place a human sees the tree before it is data.
2. Pin: HTTP only, and checkable. Zero hits in the skill dir for
   `drizzle`, `pglite`, `data/dabom`, `$lib/server`, `ingestTree`.
3. Pin: extraction and composition are two steps. A markdown document
   is a menu of candidates; a BOM is a selection from it. A heading with
   a part number is evidence, not a line.
4. Pin: request `source` carries the document path; `sku` stays absent
   so the server ladder resolves identity and seeds win.
5. Pin: on 409 / 422 the skill shows the body, edits the file, re-POSTs
   the whole file. It does not fall back to `/items` and `/bom` by hand.
6. Pin: no MPN is invented. A candidate with no part number becomes a
   name-minted node, which the route already lands as `placeholder`.
7. Refuse: one POST per heading or per section. One file, one POST,
   one transaction.
8. Refuse: a PDF path that skips the file step. A datasheet yields
   attributes for one item, rarely a tree; it still lands in the file.
9. Refuse: any browser or vendor fetch inside this skill. Prices are
   `add-price-skills`; price cells in the brief are dropped.
10. Tradeoff: the file step costs the agent one more round trip on
    every ingest. I take it. Retry becomes re-POST of a diffable
    artifact, and the crib never sees a kit nobody chose.

### The three send-back lines

**Tree file before POST.** Closed. Delta requirement "Tree file before
POST": the skill SHALL write an `IngestRequest` JSON file and SHALL NOT
POST until that file has been read. Two scenarios pin it: the production
kit scenario asserts on the file's contents, and the datasheet scenario
now says the tree *file* is what a later POST sees, where the prior text
said only that `pdf2md` ran first. Take 1 and take 8 answered.

**Candidates plus selection.** Closed. Same requirement: the parser
SHALL emit candidates (heading, optional manufacturer, mpn, notes) and
the tree SHALL be composed from a selection (named cart section,
argument list of MPNs, or hand edit), "not from every heading that has a
`PN` row". Tasks item 4 says the same in the same words. Take 3
answered. Design adds that `sku` stays absent and price cells are
dropped, which answers takes 4 and 9.

**Whole SHOPPING.md, no AGX dev kit.** Closed. Scenario "Production kit
is not the shopping menu": GIVEN the whole `SHOPPING.md`, WHEN the skill
composes the `Cart T` tree file, THEN it contains the T4000 SOM and the
Rogue-T5 and not the AGX Thor Developer Kit. Tasks item 6 names the
whole fixture and the absent dev kit. I re-read the fixture to check
the scenario is honest against it: `Cart T` lists the T4000 SOM and the
Rogue-T5 `AGX302`; the dev kit appears only under section 1 and in
`Cart S`. A parser that took every `###`+`PN` heading would put the dev
kit (`945-14070-0080-000`) and three rejected carriers in the tree, and
would miss the Rogue-T5, whose part number is in a `Carrier-only` row
rather than a `PN` row. So this one scenario fails both halves of the
old rule at once. That is the right fixture and the right assertion.

### Steelman against my take

- Take 5 (edit and re-POST, never hand-POST `/items`) is not in the
  delta. The route is idempotent and every write is one transaction, so
  the delta does not need to forbid the workaround to keep data safe.
  It is a SKILL.md line, not a requirement. Minor 3.
- Take 2 wanted `ingestTree` in the grep list. Design names it ("no
  in-process `ingestTree()`") and `$lib/server` in the grep already
  catches the only import path to it. Covered.
- Take 6 (no invented MPN) is not stated. The candidate model carries
  `mpn` from the document, and the scenario's positive assertions would
  not catch a fabricated one. But the server mints on name when `mpn`
  is null and lands the row as `placeholder`, which is the honest
  outcome, and an agent that invents part numbers is not a spec
  problem. Not a hole.

HTTP-only was pinned last pass and the amend strengthened it with

## Minor (fix at act, not blocking)

1. **Test home contradicts the delta.** Design offers two options: add
   `skills/**` to the vitest include, or put the helper under
   `src/lib/skills/`. The delta now says no markdown parser SHALL be
   added under `src/`. Only the first option is legal. Add `skills/**`
   to the include and drop the `src/lib/skills/` alternative from
   design. Reader line added to tasks.
2. **Make "file before POST" structural.** The checkable form of "SHALL
   NOT POST until the file has been read" is that the POST step takes a
   tree file path as its only input and never a source document. Then no
   code path can skip the file. Say so in SKILL.md.
3. **On non-2xx.** SKILL.md should say: show the body, edit the tree
   file, re-POST the whole file. Do not hand-POST `/items` and `/bom`
   lines around a 409, and never retag a seed floor.
4. **Rogue-T5 part number.** It sits in `| Carrier-only | PN \`AGX302\`
   ...|`, not a `| PN |` row. The scenario will fail a naive row match.
   Candidate extraction must read `PN` inside any table cell, or the
   cart selection must carry the part number from the cart line itself.
   Either is fine; the test decides.
5. **Cart lines without part numbers.** `Cart T` items 4 to 6 (PYXIS
   6K PL, RV1126 turrets, RV1126 EVB) have no MPN anywhere in the
   document. They become name-minted `placeholder` nodes. Expected, and
   worth one sentence in SKILL.md so an agent does not go hunting.
6. AGENTS.md still has no `skills/` pointer. Tasks item 7 covers it.

## Verdict
