## Required contract amendments

1. **Pin locator validation and compatibility at the ingest boundary.** Delta line 5 classifies every non-HTTP(S) locator as `notebook`; design lines 7 and 13 say to store whatever JSON names. The current schemas accept nullable, unrestricted source strings (`src/lib/server/api/schemas.ts:348,363`). The proposed `add-evidence` contract instead accepts repository-relative paths or absolute HTTP(S) URLs and deduplicates after trim. An empty string or `file:///tmp/brief.pdf` therefore has no agreed ingest outcome. Specify omitted/null handling, blank handling, accepted locator forms and kinds, trim-based identity, and the validation response for unsupported input. Make any narrowing of legacy source strings explicit. Add API scenarios for invalid evidence leaving the entire tree unchanged and whitespace-equivalent locators sharing one source. Reusing the dependency's validator is a good implementation choice, but the ingest contract must state its externally visible result.

2. **Define enrichment values against actual create/null-fill behavior.** Delta line 7 and design line 19 use payload values that are “non-empty,” without specifying normalization. Existing creates trim manufacturer and MPN and turn whitespace-only values into null; matches also trim before writing (`src/lib/server/bom.ts:600-603,634-636`). Notes are stored without trimming. For example, `manufacturer: "   "` can satisfy literal string non-emptiness while persisting no manufacturer, and `mpn: " ABC "` persists `ABC`. Pin whether evidence records the persisted value or an intentionally raw observation, and prevent an enrichment claiming a manufacturer/MPN write that did not occur. Pin notes eligibility separately without changing item behavior. Add create and match scenarios for padded and whitespace-only values and assert exact enrichment values, not just row counts. Recording the persisted value is the smallest fit with the stated purpose, but an explicit alternative can be reviewed.

3. **Apply a source-selection rule to matched enrichments explicitly.** The node-source/request-source/null rule appears only in the create paragraph (delta line 7; design line 19). The match paragraph specifies eligibility but never selects its source. An existing item may retain source A while this request fills a null manufacturer from source B; citing the retained column would misattribute the new fact. State the rule for both paths, including no singular source, and pin which sources link to each node. Add a scenario with request source A, a node override B, and a child without an override: the child must retain the existing request-source inheritance behavior (`src/lib/server/bom.ts:777`), while the matched node's new fact cites its current supporting document. Include the case where an old non-null `items.source` is preserved. Supplemental `sources[]` links need not become field citations.

## Steelman and disposition

A careful implementer could infer trimming from the existing item writes, inherit validation from `add-evidence`, and apply the create attribution rule to matches. That is the strongest case for accepting this lean contract. However, different reasonable implementations would produce different append-only history or reject previously accepted requests. Those choices belong in the contract and its API scenarios before implementation.

The declared transaction and idempotency requirements are sufficient architectural direction; this review does not prescribe helper signatures or a database uniqueness strategy. The existing MPN-fill scenario should use a matchable fixture consistent with current identity guards, rather than change identity resolution to make the scenario pass.
