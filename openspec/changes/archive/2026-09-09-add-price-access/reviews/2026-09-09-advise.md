## Independent take (written before design.md / tasks.md / delta)

Sources: proposal Why + steer, living spec stub, `schema.ts:69-88`, `bom.ts:24-26` and `bom.ts:84-140`, `api/app.ts:416-458`, `db/catalog.ts` seed.

1. Pin: `method` is a closed enum on `quotes` (`seed | api | crawl | headed | manual`), not free text. Roll-up and the UI must be able to rank it.
2. Pin: the ladder is per vendor, not global. Digi-Key/Mouser/Arrow start at API; CTI/WDL/B&H start at crawl. A vendor's first rung is data on `vendors`, not code in an adapter.
3. Pin: a lower rung never masks a higher one. A `crawl` row for Digi-Key written while the API was down must not become the preferred row by being newest.
4. Pin: `checkedAt` becomes a real instant (timestamptz, NOT NULL), not a nullable `date`. "As-of" with no time and no zone is not an as-of.
5. Refuse: append-only in the proposal while `PATCH /quotes/{id}` still lets `priceCents` change. Either PATCH loses price/url/checkedAt, or the proposal is not append-only. Also `DELETE /items/{sku}` cascades quotes today (`app.ts:195`).
6. Refuse: `isPreferred` as a per-row flag under append-only. Every refresh would have to move the flag. Preferred belongs to (item, vendor), or the row set must be read as "latest row per vendor, then preferred vendor".
7. Refuse: `pickQuote` unchanged. It uses array order and ignores as-of; with many rows per vendor it returns whichever row the DB happened to return first.
8. Tradeoff: append-only is honest but the seed becomes one more `method=seed` row per quote, and the existing seed's `is_preferred` rows need a backfill of `method`/`checkedAt`. Accept the growth; pin the backfill.
9. Missing: a staleness rule. Roll-up should surface `asOf` = min(checkedAt) across chosen quotes, or a `stale` flag, so the total says how old it is.
10. Test I want: Digi-Key has an `api` row dated Sep 1 and a `crawl` row dated Sep 8, both priced. Roll-up picks the Sep 1 `api` row. A second test: two rows same vendor same method, newer wins.

## Compare (after design.md, tasks.md, delta)

Answered by the author:

- Take 1 — method is a closed enum. Delta and tasks say `api | crawl | headed | seed`. Design.md still says three values; delta wins, design.md should match. `manual` is absent: the CTI "quote with the carrier" seed row is a human-typed quote, not a seed placeholder. Add it or say seed covers it.
- Take 2 — per-vendor ladder. Design says B&H / CTI / WDL start at rung 2 or 3. Stated in prose, not as data. Acceptable here because adapters live in `add-price-skills`; that change must put the first rung on `vendors`, not in adapter code.
- Take 4 — as-of type. Tasks say "checkedAt already exists — keep or alias". Date-only is defensible for street prices. Pin one name (`checkedAt`) and stop there; do not alias.
- Take 8 — seed backfill. Tasks list `seed` as a method. Fine.
- Ladder order API → crawl → headed is pinned in the delta as a SHALL. This is what the packet asked me to confirm. It is there.

Not answered. These are the holes.

### Hole 1 — the preferred row outlives the refresh (take 6, take 7)

The Why is "seeded street prices rot". The delta scenario says: existing
preferred quote, POST a new price, "roll-up uses the preferred row until
it is changed". So an API refresh inserts an unpreferred row and roll-up
keeps the rotted seed row. The refresh changes nothing the total can see.

There is no rule for what a new row does to the older row for the same
(item, vendor). Nothing stops two preferred rows on one item; `pickQuote`
then returns whichever the DB yields first. The tasks test "preferred
still drives roll-up" would bake this in.

Steelman: preferred is a human choice, and the adapter will flip flags.
That takes three non-atomic calls (POST, PATCH old false, PATCH new
true) through the public API, and the delta says nothing about it.

Fix the delta, one of:

- (a) A new row for the same (item, vendor) supersedes: it inherits
  `isPreferred` from the row it replaces and that row's flag clears.
  Roll-up reads latest row per vendor, then preferred vendor.
- (b) Move preferred to (item, vendor) — a `preferredVendorId` on
  `items` or a unique partial index on `(item_sku) WHERE is_preferred`.

Either works. (a) touches less. Pick one and write the scenario.

### Hole 2 — append-only with a price PATCH (take 5)

Tasks: "OpenAPI Quote create/patch include method and url". `PATCH
/quotes/{id}` today sets any column, including `priceCents`. That is not
append-only. Pin: PATCH is `isPreferred`, `notes`, `inStock` only.
Price, URL, method, checkedAt are immutable after insert.

### Hole 3 — fallback ignores method (take 3)

Delta: "else the latest priced quote". A `crawl` row dated Sep 8 beats an
`api` row dated Sep 1 for the same vendor. The ladder says API is the
truer source. Pin the fallback: latest per vendor, then by method rank
`api > headed > crawl > seed`, then newest. Or state that within a vendor
the newest wins regardless of method and accept that a crawl can shadow
an API row. Say which.

### Minor

- Login-wall scenario: "the recorded outcome is not an empty fail with no
  method". Failed attempts are not quotes. Do not write a priceless
  quote row to record a failure; record it elsewhere or not at all in
  this change.
- Roll-up should carry an `asOf` (min `checkedAt` across chosen quotes)
  so the total says how old it is. Not blocking.

## Verdict reasoning

The ladder is pinned. What is not pinned is what a refresh does to the
roll-up, and that is the whole point of the change. Holes 1 and 2 are
two scenarios and one sentence in the delta plus one line in tasks. Not
a redesign. Send back for those; hole 3 can be answered either way in
the same edit.
