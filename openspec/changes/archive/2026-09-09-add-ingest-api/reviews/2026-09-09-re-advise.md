## Blind take (written before opening delta, design.md, tasks.md, prior review)

Sources: packet Why, living spec stub (empty), `schema.ts:48-70` and
`120-139`, `app.ts:133-151`, `bom.ts:15-31`, `99-105`, `348-398`,
`schemas.ts:81-103`, `app.ts:503` (transaction already in use).

1. Pin: every node carries a client `sku`; no minting (matches POST /items). Identity order is sku hit, then exact (manufacturer, mpn), then create. Never name similarity.
2. Pin: the whole tree runs in one `db.transaction`; any 4xx on any node rolls the whole request back. No partial BOM lands.
3. Pin: 201 body lists every item touched with created vs reused, plus every line, so an agent can verify a typo'd sku did not attach the wrong existing item.
4. Pin: a node with children and floor != assemble is rejected at validation before any write (422 with the node path), or floor is forced to assemble. Either, but pinned.
5. Pin: an existing sku is reused, not 409'd, so a re-run after fixing one line succeeds; and ingest does not overwrite the existing item's fields (no PATCH-through).
6. Pin: duplicate (parent, child, role) within the request or against existing lines is a 409 for the whole request; cycle check runs over existing plus new lines.
7. Pin: free text from the brief (notes, source URL) rides through to items.notes / items.source rather than being dropped; the route is where markdown-derived prose lands.
8. Refuse: draft store, server-side markdown parser, skill-side SQL, fuzzy identity, manufacturer-only match.
9. Tradeoff: reuse-by-sku is convenient but silently attaches on typo; the created/reused split in the body is the mitigation, not a warning field.
10. Cap nodes per request (422 over the cap); wouldCycle per line is O(n * depth) queries inside one transaction, fine at the cap.

## Compare (after delta, design.md, proposal.md, tasks.md, steer.md, prior review)

### The four send-back holes, checked against SHALL + scenario

**Hole 1, identity edges.** Closed.
- (a) MPN-only when incoming manufacturer is null, exactly one row else
  409: SHALL in "SKU mint and collision". No dedicated scenario; "Seed
  identity wins" does not say whether the node carries a manufacturer.
  See minor 2.
- (b) name-minted slug hitting a row with no pair reuses that row:
  SHALL. "Repeat POST" is the scenario that depends on it and now holds.
- (c) supplied kebab sku that is new is created as given, 422 if not
  kebab: SHALL. Covered by "JSON tree becomes a kit" in spirit.
- (d) matched rows not overwritten, fill nulls only for manufacturer,
  mpn, source: SHALL, and "Seed identity wins" asserts seed name and
  status survive. This was the dangerous one and it is nailed.

**Hole 2, atomicity.** Closed. "Any non-2xx response SHALL write
nothing" plus one transaction. Three scenarios assert nothing written:
"Failed child writes nothing", "Cannot explode a buy SOM", "Name
collision with an identified part".

**Hole 3, 201 body.** Closed by scenario. "JSON tree becomes a kit"
pins per-node `sku`, `action` created | matched, `floor`, line ids.
Design "Response" matches. The requirement paragraph has no SHALL
sentence for the body; the scenario is the test, so this is wording.
See minor 3.

**Hole 4, markdown.** Closed. JSON only, markdown and PDF 415, parsers
tracked in `add-ingest-skills`. Steer records it. Scenario covers PDF
only; markdown 415 is SHALL without scenario. Acceptable.

### Steelman against my take

- Take 1 wanted sku first. Author puts pair match first and reuses the
  seed sku even when the payload supplied a different one, reporting
  it as `matched`. That is better for the Why: a brief with a real MPN
  must not fork a seed row because the agent guessed a sku. Accepted;
  the `action` field is the mitigation my take 9 asked for.
- Take 4 offered 422 or auto-promote. Author auto-promotes new nodes to
  `assemble` and 409s existing `foundry`. Pinned, and it keeps
  `addBomLine`'s door. But see the one real defect below.
- Take 6 wanted 409 on duplicate (parent, child, role). Author chose
  set-qty on the index key. Better for re-runs, and the prior review
  asked for exactly this. Accepted.
- Take 7 (prose rides through): `source` is filled on name-minted
  creates. `notes` on lines is in the existing `bom_lines` shape.
  Fine.
- Take 10 (cap): not stated. Lean density; not a spec hole.

### One real defect, fixable in a sentence

The floor requirement contains two SHALLs that disagree on the same
input. "SHALL set a node that lists children to `assemble` ... when
that node is new or currently `buy`" and, next sentence, "SHALL reject
ingest that would hang children on an existing `buy` ... item with
409." An existing `buy` item with children in the payload is both
promoted and rejected. Design carries the same pair of sentences. The
scenario "Cannot explode a buy SOM via ingest" decides it: seed
`t4000-som` is `buy`, attaching a child is 409. So the binding reading
is: promotion applies to **new** nodes only; an existing `buy` or
`foundry` parent is 409. Strike "or currently buy" from the delta and
design before fold. The prior review's take 5 introduced the phrase,
so this is on the reader as much as the author. Not a send-back:
the scenario is unambiguous and act can implement against it.

### Minor

1. Supplied sku that exists with a pair, while the incoming node has no
   pair (agent references `t4000-som` by sku alone). Design step 3
   handles "row has no pair" and "different pair" but not "incoming has
   no pair". Pin: a null incoming pair is never a different identity;
   the node matches. Otherwise the most basic reference form 409s.
2. Add one MPN-only scenario: node with mpn `900-13834-0000-000`, no
   manufacturer, no sku, matches `t4000-som`; and a second with two rows
   sharing an MPN is 409.
3. Add a SHALL sentence for the 201 body to "Ingest writes through" so
   the fold carries it as a requirement, not only a scenario.
4. Design says name-minted creates keep `status: placeholder` unless
   the payload set one. `ItemCreateSchema` defaults `status` to
   `candidate`, so the ingest node schema must default differently or
   the design is wrong. Say which. `placeholder` is a valid status.
5. Cycle guard. Delta and design do not say ingest lines pass
   `wouldCycle`. A payload can close a cycle through an existing
   `assemble` item by sku reference. Pin: lines are inserted through
   `addBomLine` (or the same guard) inside the transaction, with the
   transaction handle, not the pool.

These are reader-added tasks in `tasks.md`.

## Verdict

Accept. Identity order is pinned in four steps with the null-pair,
MPN-only, supplied-sku, and no-overwrite edges each a SHALL. Atomic
rollback is a SHALL with three scenarios asserting nothing written.
201 body and JSON-only are pinned. No draft store, no markdown parser
on this route. One contradictory phrase in the floor SHALL is settled
by its own scenario and is one strike-through before fold.
