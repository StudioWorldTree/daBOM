## Independent take (written before design.md / tasks.md / delta)

Sources: proposal Why + steer, living spec stub, `schema.ts:48-61` and
`117-139`, `api/app.ts:133-151`, `bom.ts:29-30` and `348-372`,
`api/schemas.ts:3-8` and `81-100`, ADR-002.

1. Pin: one identity rule, in order. Client `sku` in the node wins if
   present; else `slug(manufacturer)-slug(mpn)` when both are non-null;
   else `slug(name)`. Specify `slug` once: what happens to `/ . _ +`,
   unicode, repeated dashes, leading dash, length cap. ADR-002's regex is
   the contract; the slug must always satisfy it or the node is 422.
2. Pin: the collision rule, split by how the sku was minted. Minted sku
   exists and the existing row has the same (manufacturer, mpn) → match,
   reuse, do not overwrite name/kind/category/floor. Exists with a
   different or null pair → 409 naming the sku. Name-minted skus are the
   dangerous case ("power-supply" recurs across briefs): match only when
   the existing row has no manufacturer/mpn either; otherwise 409.
3. Pin: identity match must also look up by (manufacturer, mpn) when the
   existing row was hand-authored under a different sku (seed rows like
   `t4000-som` carry a real mpn). Otherwise ingest mints a second sku for
   the same part. Both columns are nullable; match only when both set.
4. Pin: one transaction per ingest call. A failed line after ten item
   inserts must leave zero orphan `candidate` rows. Any 409/422 rolls
   back the whole tree.
5. Pin: floor promotion is bounded. A parent that receives children
   becomes `assemble` only if it is new or currently `buy`. An existing
   `foundry` parent is a hand decision; 409, do not retag. No touching
   seed items' floor beyond the node being ingested (LEARNINGS: seed
   retag is a migration, tracked as `add-floor-seed`).
6. Pin: idempotency. Re-posting the same brief must not duplicate lines.
   `bom_parent_child_role_uidx` will throw on the second POST unless the
   route treats an existing (parent, child, role) as set-qty. Say which:
   I want set, not add.
7. Refuse: markdown shopping-brief text as a second input format on this
   route. Parsing prose into a tree is extraction, and LLM extraction is
   out of scope, so what is the grammar? Either pin a strict grammar with
   tests or move markdown to `add-ingest-skills` and keep the route
   JSON-only. Two parsers on a route with an untested identity rule
   doubles the surface.
8. Refuse: a 201 with nothing but the root item. The caller is an agent;
   it needs per-node `sku` and `action: created | matched` and the line
   ids, so it can report and so the next brief can reference by sku.
9. Tradeoff: name-mint is required (most brief lines have no MPN) and it
   makes a global namespace of name-slugs that will collide as the
   catalog grows. Accept it; pin that a name-minted row is marked
   (`source` = the brief, or `status=placeholder`) so it is telling
   apart from an authored one, and that a later manufacturer+mpn is a
   PATCH, never a re-mint.
10. Test I want: one POST where the root is new, child A matches a seed
    item by (manufacturer, mpn) under a different sku, child B name-
    collides with an existing item that has an mpn. Expect: 409 for B
    and nothing written. Drop B: root created `assemble`, A attaches to
    the seed sku with no new row, response says `matched` for A.

## Compare (after design.md, tasks.md, delta)

Also read: `catalog.ts:27-55` (seed `t4000-som` carries NVIDIA +
`900-13834-0000-000`, status `preferred`), `app.ts:503`
(`db.transaction` already in use for quote POST), and the real brief
`../AICamera/docs/SHOPPING.md` that the Thor scenario excerpts.

What the packet asked me to confirm:

- Write-through vs draft: pinned. Delta "Ingest writes through" SHALL
  NOT keep a draft store; design says the same; steer records the user
  decision. Accepted as the ingest path.
- Identity collision: partly pinned. See Hole 1.

Answered by the author:

- Take 3 — pair match reuses the seed sku under a different name. Design
  step 2, delta "Seed identity wins". Case-insensitive, trimmed. Good.
- Take 5 — floor promotion bounded. New node with children → `assemble`
  before lines; existing `buy`/`foundry` leaf → 409; never wipe
  `assemble` back to `buy` while children exist. Good, and it agrees
  with `addBomLine`'s 409 door.
- Take 6 — repeat POST does not duplicate lines. Delta "Ingest is
  idempotent". Note: design matches on `(parentSku, childSku)` but the
  index is `(parent, child, role)`; match on the index key or two roles
  of one child collapse. Say whether a changed `qty` on re-POST is set
  or ignored. Not a hole; a sentence.
- Take 7 — markdown is bounded to `###` + `PN` row, not extraction.
  Bounded, yes. But see Hole 4.
- Take 9 — name-mint accepted with `-2` suffix. Accepted as a tradeoff.
  Marking name-minted rows (`source` = brief path, which the seed
  already does with `CAR`) is one line in tasks; add it.

Not answered. These are the holes.

### Hole 1 — identity rule has four undefined edges (takes 1, 2)

Design steps 1–5 read as a complete order but leave out the cases the
Why actually hits. A brief line is mostly a name, sometimes a PN, rarely
a manufacturer field.

(a) MPN-only match. Design step 2 needs manufacturer AND MPN. The
markdown grammar yields only `PN`; the heading `NVIDIA Jetson T4000 SOM
(the module)` has no manufacturer row. So the markdown path cannot reach
step 2, falls to step 4, and mints `nvidia-jetson-t4000-som-the-module`.
The tasks test "NVIDIA 900-13834-0000-000 reuses `t4000-som`" only
passes on the JSON path. Pin: match on MPN alone when the incoming
manufacturer is null and exactly one existing row has that MPN; two
rows with that MPN and no manufacturer is 409.

(b) Null-pair collision. Step 5 suffixes on "a different identity".
When neither the existing row nor the incoming node has a
(manufacturer, mpn) pair, is that the same identity or different? SQL
says null ≠ null. If different, re-POSTing a brief whose children are
name-only mints `power-supply-2`, `-3` on every run, and the "Repeat
POST" scenario fails (the kit gets four lines, not two). If same, a
second brief's unrelated "Power Supply" silently attaches to the first
brief's item. Pick: name-minted slug hitting a row with no pair is the
same identity → reuse. That makes the idempotency scenario true and
must be written down, with the second-brief consequence acknowledged.

(c) Supplied sku that does not exist. Step 3 reuses a supplied sku only
"that exists". A supplied kebab sku that is new falls to step 4 and is
silently replaced by a minted one. POST `/items` honors the client's
sku; ingest must too. Pin: supplied sku is created as given, 422 if not
kebab.

(d) Matched rows are overwritten. Design "Idempotence": "upsert item
fields that the payload set". `ItemCreateSchema` defaults `status` to
`candidate` and `description` to `''`; a zod-parsed node has those
"set". A brief that matches `t4000-som` would flip the seed from
`preferred` to `candidate` and rename it to the heading text. Pin:
ingest never modifies a matched existing row except the floor promotion
already covered; at most fill nulls (`manufacturer`, `mpn`, `source`).
Add a scenario asserting the seed row's `name` and `status` survive.

### Hole 2 — atomicity is not stated (take 4)

"One request" is not "one transaction". A tree of twelve nodes where
node nine 409s leaves eight `candidate` items and some lines behind,
with no draft store to hold them. That is the worst point between draft
and write-through. `db.transaction` is already used at `app.ts:503`.
Pin a SHALL: any non-2xx writes nothing. Extend "Cannot explode a buy
SOM" to assert that the new root from that body was not created.

### Hole 3 — no response contract (take 8)

Nothing in design, delta, or tasks says what `POST /ingest` returns.
The caller is an agent that has to name what it just made in its next
call and report matched-vs-minted skus to a human. Pin the 201 body:
the tree echoed with `sku`, `action: created | matched`, `floor`, and
line ids per node. Add it to the "JSON tree becomes a kit" scenario.

### Hole 4 — the markdown grammar mints junk on a real brief (take 7)

Design: every `###` heading is an item. In the real `SHOPPING.md` the
`###` set includes "Cart S — software this week", "Cracking one open",
"Breakout board in the CTI sense", and the Rogue-T5 section's PN sits
in a `| Carrier-only | PN AGX302 |` row that the `PN`-label rule misses.
The delta scenario passes because it posts a curated excerpt. A real
POST of the brief writes six nonsense items straight to the catalog
with no draft to review. Two options; pin one:

- Only a `###` section that has a `PN` row becomes an item; other
  headings are ignored. Then say how the root kit is named (body
  wrapper, query param, or first `#`/`##`) and that all items nest flat
  under it with qty 1.
- Or drop markdown from this route and let `add-ingest-skills` turn
  markdown into the JSON tree. The route keeps one parser and one
  identity rule.

I lean to the second. The Why is satisfied by JSON write-through; the
markdown parser is a convenience that adds a second untested surface to
the same change that carries the identity rule.

### Minor

- `slug` of a name that is all symbols is empty and fails the ADR-002
  regex. Say 422.
- Design step 2 above step 3 means a supplied sku is ignored when the
  pair matches another row. Defensible; say it and report it via the
  response `action`.
- Tasks lack a collision test. Add take 10's shape once Hole 1 is
  decided.

## Verdict

Send-back. Write-through is pinned and is the right path. Identity is
where the change earns its name and it has four undefined edges, one
of which (b) makes the delta's own idempotency scenario undecidable.
Atomicity and the response contract are each one SHALL. Markdown is
either bounded to PN-bearing sections with a stated root, or moved to
the skills change. Fix the delta and design, re-advise.
