## Independent take (written before proposal / tasks / steer / delta)

Sources: packet Why, `openspec/specs/bom-ingest/spec.md`, the
`ingest-skills` living stub, `api/app.ts:578-621`, `api/schemas.ts:328-390`,
`hooks.server.ts`, AGENTS.md, and the head of AICamera `SHOPPING.md` /
`CAMERAS.md`. No skill directory exists in the repo yet.

1. Pin: the skill's only write path is `POST /api/v1/ingest` over HTTP to a
   running server. It never opens `data/dabom`, never imports drizzle or
   `$lib/server`, never calls `ingestTree()` in-process. Say it as a MUST
   NOT and make it checkable: no `data/` path and no server import in any
   skill file.
2. Pin: the skill reads the contract from `/.well-known/openapi.json`
   (`IngestNode`), not from a schema pasted into the skill. An example
   tree is fine; a second copy of the field list will drift.
3. Pin: the product of the skill is a JSON `IngestRequest` file on disk
   that a human reads before the POST. Ingest is write-through with no
   draft store, so the tree file is the review artifact and the POST is
   the commit. No skill step goes from source doc to POST without the
   file in between.
4. Pin: the field mapping for each source. SHOPPING.md `PN` row → `mpn`,
   table heading → `name`, doc path → request `source`. Seeded parts are
   referenced as bare `{ "mpn": ... }` so seed identity wins and nothing
   is overwritten. Price cells are dropped: ingest SHALL NOT write quotes.
5. Pin: on 409 / 422 the skill shows the body, edits the tree, re-POSTs
   the whole tree (idempotent). It never works around a 409 by hand
   POSTing `/items` and `/bom` lines, and never retags a seed floor.
6. Refuse: PDF or markdown parsing as product code. No `pdf-parse` or
   markdown dependency in `package.json`, no parser module under `src/`.
   Reading the datasheet is the agent's job; the skill says what to
   extract and where it goes in the tree.
7. Refuse: skill-side SKU minting. `sku` stays absent unless the human
   names one. The server's identity ladder decides; two minting rules
   would drift.
8. Refuse: a Claude-only home. Author is Grok, and Codex will read this
   too. The skill is plain markdown at a path AGENTS.md names, loadable by
   any harness, not a `.claude/` plugin.
9. Tradeoff: one skill with three source recipes (shopping brief,
   CAMERAS.md, datasheet PDF) versus three skills. Extraction differs,
   the target tree does not. I take one skill, one contract, and accept a
   longer file.
10. Open: base URL and auth. No auth on `/api` today. The skill takes a
    base URL (default `http://localhost:5173/api/v1`) and says nothing
    about tokens yet; IdentiKey device flow gates it later, do not invent
    a token step now.

## Compare (after proposal, steer, tasks, delta)

Also checked: `vite.config.ts` (vitest includes `src/**` only),
`package.json` (no pdf or markdown dependency), `pdf2md` on this host
(`~/.cargo/bin/pdf2md`, present), `DELETE /items/{sku}` and
`DELETE /items/{sku}/bom/{lineId}` (exist, so a wrong ingest is
undoable by hand), the full heading list of AICamera `SHOPPING.md`, and
the `add-ingest-api` re-advise hole 4.

**Take 1, HTTP-only.** Pinned. The delta says SHALL NOT import drizzle,
SHALL NOT open `data/dabom/`, SHALL NOT run SQL, and the scenario asserts
the kit lands without a skill-side database write. Proposal and steer
say the same. This is the thing the packet asked me to confirm and it
is answered.

**Take 6, no parser as product code.** The steer decided the markdown
parser lives with the skill, not on the route, and the delta keeps PDF
bytes out of the skill by routing through `pdf2md`. I accept a helper
script under `skills/ingest-hardware/`. That is not `src/`, and the
route stays 415 for markdown. Fine.

**Take 7, no skill-side sku.** Tasks map `###` heading to name and the
`PN` row to mpn and say nothing about sku. The server ladder mints.
Matches.

**Take 8, harness-agnostic home.** `skills/ingest-hardware/SKILL.md`,
plain path. Matches. AGENTS.md does not yet point at `skills/`; see
minor 1.

**Take 10, base URL, no auth.** Tasks: base from env or
`localhost:5173`. No token step. Matches.

**Take 2, contract from the well-known spec.** Tasks put a "tree shape"
in SKILL.md. Not addressed. Minor 2.

**Take 3 and 4, tree file before POST, and the field mapping.** Not
addressed, and this is where the hole is.

### Steelman against my take

- Take 6 wanted zero parser code. The steer's answer is better for the
  Why: an agent with no helper will write its own extractor each time,
  and the extractor is where the SQL temptation lives. A small script
  that emits an `IngestRequest` is the cheapest way to make HTTP the
  path of least resistance. Accepted.
- Take 9 wanted one skill with three recipes. The change is one skill,
  and folds PDF into the markdown path via `pdf2md`. Cleaner than my
  version. Accepted.
- Take 3 asked for a tree file on disk before POST. One could argue the
  route's atomicity, idempotency, and 409 guards make preview
  unnecessary, and DELETE exists for cleanup. That argument holds for
  identity and floor errors. It does not hold for the error below,
  which the route cannot see because every node in it is valid.

## Hole

**The markdown rule maps a menu as a BOM.** Tasks item 4 says
"`###` + `PN` row becomes an item; other headings ignored; root from
`#`/`##` or argument". Run that over the document the Why names.
`SHOPPING.md` has a `###` with a `PN` row for the T4000 SOM, for the AGX
Thor Developer Kit (whose heading says "not a T4000"), and for the
Gauntlet, FORECR and Auvidea carriers that the brief rejects. The
preferred carrier's PN sits in a `| Carrier-only | PN \`AGX302\` ...|`
row, which the rule misses. The actual kit is the `### Cart T` section
near the bottom, which has no `PN` rows of its own. So the rule as
written produces a valid tree, every node passes the route, and the
crib gets a kit containing one SOM, one wrong dev kit, and four carriers
the team is not buying. The test in tasks item 5 uses "a Thor shopping
excerpt", which is exactly the input on which the rule looks right.

The `pdf2md` path has the same shape. A datasheet converted to markdown
has no `PN` table rows in the SHOPPING.md style, so "the same markdown
to tree path" yields nothing or the wrong thing, and the delta's
scenario for PDF only asserts that `pdf2md` ran first.

What closes it, and it is small:

1. Delta: add a requirement that the skill writes the `IngestRequest`
   JSON to a file and the agent (or human) reads it before the POST.
   The file is the review artifact; the POST is the commit. Scenario:
   given SHOPPING.md, the tree file for the production kit contains
   `t4000-som` and the Rogue-T5 and does not contain the AGX Developer
   Kit.
2. Tasks item 4: the parser emits candidates (heading, manufacturer
   where the heading gives it, mpn, notes) and the tree is composed
   from a selection: a cart section, an argument list of MPNs, or the
   agent's hand edit of the tree file. It is not "every `###` with a
   `PN` row under one root".
3. Tasks item 5: test against the whole `SHOPPING.md` fixture, not an
   excerpt, and assert the dev kit is absent from the production kit.

This does not reopen HTTP-only, the route, or the sku ladder. It is one
requirement and two task lines.

## Minor (fix at act, not blocking)

1. AGENTS.md has no pointer to `skills/`. Add one line so a Grok or
   Codex session finds the skill without being told.
2. SKILL.md "tree shape": link `/.well-known/openapi.json` `IngestNode`
   and carry one example tree, not a second copy of the field list.
3. Tests have no home. Vitest includes `src/**` only. Either add
   `skills/**` to the include or put the helper under `src/lib/skills/`
   with the SKILL.md importing nothing from `$lib/server`. Say which.
4. "A mocked drizzle import is not in the skill" is not a checkable
   test. The checkable form is a grep over `skills/ingest-hardware/`
   for `drizzle`, `data/dabom`, `pglite` and `$lib/server`, asserting
   zero hits.
5. Price rows in the brief are dropped; say so in SKILL.md so an agent
   does not push them into `notes`. Quotes are `add-price-skills`.
6. Manufacturer is in the heading, not a table row, in SHOPPING.md.
   Carry it when the heading names one so pair match beats MPN-only.

## Verdict

**send-back.** HTTP-only is pinned in the delta with a SHALL NOT for
drizzle, the data file, and SQL, and a scenario that asserts it. That
part is done. The markdown rule in tasks would, on the document the Why
names, write a syntactically valid kit of rejected alternatives through
a route that cannot tell, with no file between the source and the POST.
One added requirement (tree file before POST, composed from a selection)
and two task edits close it. Re-advise on those three lines only.
